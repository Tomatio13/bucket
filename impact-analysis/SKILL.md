# Impact Analysis

実装を始める前に、要求された変更がどこへ波及しそうかを特定する。

## Quick start

ユーザーが変更要件を渡したら、次を行う。

1. 求められている振る舞いの変更を1文で言い直す
2. 関連するエントリポイントと境界をコードベースから探す
3. 下流の依存先と上流の呼び出し元を追跡する
4. 影響箇所、リスク、必要なテストを要約する

要件が曖昧なら、振る舞いの変化を特定するために必要最小限だけ質問する。

## Workflow

### 1. 変更内容を定義する

- 現在の振る舞いを定義する
- 望ましい振る舞いを定義する
- 必須要件と仮定を分ける
- ユーザーが境界を示しているなら、明示的に対象外も書く

振る舞いの変更が曖昧なまま、早すぎる段階でコードに飛び込まない。

### 2. 起点になりそうな入口を探す

この振る舞いがシステムに入ってくる高いレベルの入口を探す。

- UI画面、ルート、コマンド、ジョブ、APIハンドラ
- サービス境界と公開インターフェース
- 変更に関わる設定、スキーマ、イベント契約

低レベルなヘルパーではなく、観測可能な振る舞いから追い始める。

### 3. 双方向に影響を追う

各入口候補について、次を調べる。

- **下流の依存先**: service、repository、adapter、validator、serializer、job
- **上流の呼び出し元**: route、component、command、scheduler、外部連携
- **横断的な契約**: database schema、API payload、feature flag、permission、cache、analytics

推測の内部詳細より、公開インターフェースと実際の呼び出し経路を優先する。

### 4. 影響を分類する

調査結果を次に分ける。

- **直接影響**: ほぼ確実に変更が必要なコード
- **間接影響**: 振る舞い変更に依存しており、調整が必要かもしれないコード
- **要確認**: 変更は不要かもしれないが、テストで確認すべきコード
- **非影響の想定**: 近くにあるが、おそらく変えない方がよい領域

推測が混ざる箇所は、不確実性を明示する。

### 5. リスクを評価する

次を強調する。

- 契約や共有型の破壊
- モジュール間の隠れた結合
- 移行や段階リリースの懸念
- 後方互換性の懸念
- 影響範囲に対するテスト不足

より安全な小さい変更単位に分けられるなら、それを提案する。

## Output format

次のセクションを持つ簡潔なレポートを返す。

1. **変更要約**: 求められている振る舞いの変更を平易に要約
2. **影響候補**: どのモジュールやサブシステムに影響しそうか、その理由
3. **契約影響候補**: schema、API、event、config、permission など
4. **リスクメモ**: 回帰、曖昧さ、ロールアウト懸念
5. **テスト観点**: 何を検証すべきか
6. **次の一手**: 今すぐ実装する、追加調査する、変更を分割する

ローカル実装で役立つならファイルパスを併記してよいが、まずは振る舞いベースで説明する。

## Rules

- 深い実装案に入る前に、まず広く影響をマッピングする
- 可能性しか分からない箇所を断定しない
- 変更が必要なコードと、テストだけ必要な領域を分ける
- 影響が広いなら、小さくレビューしやすい単位を優先する
- 不明点は散文に埋めず、早めに表に出す
